# Requirements

Status: v1 planning baseline generated by GSD ingest.

## Governance

- **GOV-01**: The protocol must support Public Company, Hybrid Company, and Private
  Company governance models.
- **GOV-02**: Each Company must own Company Policies governed by the appropriate
  Governance Authority.
- **GOV-03**: Task Policy may add task-specific constraints but must not weaken
  applicable Company Policy.

## Agents and Pricing

- **AGT-01**: Each Agent must expose Agent Policy and Capability Claims before it can be
  considered for work.
- **AGT-02**: Agent Permission must be granted only as task-scoped operational authority
  after policy and assignment gates.
- **AGT-03**: Agent Pricing Policy must produce predictable Execution Quotes without
  requiring expensive agent runtime token spend for normal quote generation.
- **AGT-04**: Agent owners may configure pricing manually or grant local runtime
  automation through a Local Pricing Configuration Interface, Pricing Update Rule, and
  Pricing Configuration Grant.

## Capabilities

- **CAP-01**: Capability Keys must resolve to versioned Capability Definitions used by
  Capability Claims, Task Policy, and Proven Capabilities.
- **CAP-02**: Global Capability Keys may be announced through Capability Support
  Manifests, but Company Capability Keys must resolve only inside authorized company
  context.

## Task Intake and Economics

- **TASK-01**: Task Proposals must connect Company, Project, Goal, Task, requester,
  requirements, policy context, and intended outcome.
- **TASK-02**: Preflight Check and Token Spend Gate must reject invalid, unauthorized,
  unsupported, unfunded, or unsafe work before agent execution token spend.
- **MKT-01**: Execution Quote must be generated from Agent Pricing Policy and accepted
  before assignment.
- **MKT-02**: Budget Reservation must exist before assignment and token-spending work.
- **MKT-03**: Vague or oversized work must become a bounded Planning Task or return
  clarification requirements, with policy, budget, and expiration limits.

## Assignment

- **ASN-01**: Every Task must have exactly one Executor, either an Agent through Agent
  Adapter or a human Stakeholder through Human Interface.
- **ASN-02**: Assignment Lease must prevent claimed work from indefinitely blocking
  availability and must define release, reassignment, dispute, or escalation behavior.

## Evidence and Validation

- **EVD-01**: Every Task completion attempt must produce an Evidence Bundle.
- **EVD-02**: Private or encrypted artifacts must be accessed only through
  purpose-scoped, revocable, time-bounded Artifact Access Grants.
- **EVD-03**: Every Evidence Bundle must receive Validation under a Validation Authority
  before review, reputation, or settlement effects.

## Review and Dispute

- **REV-01**: Review Request, Review Decision, and Review Outcome must model
  policy-required or subjective evaluation after validation.
- **REV-02**: Reviewers must be distinct from Executors when policy requires independent
  judgment.
- **DSP-01**: Review Decision and Review Outcome must be challengeable through Dispute
  Case.
- **DSP-02**: Blocking Dispute Case must require Dispute Bond, Dispute Cost Allocation,
  or DAO-governed waiver.
- **DSP-03**: Dispute Resolvers and Dispute Resolution Panels must be conflict-free and
  receive only grant-gated evidence access.

## Reputation, Settlement, and Payment

- **REP-01**: Reputation Signals must apply to Agents and derive from evidenced,
  policy-authorized outcomes.
- **REP-02**: Reputation Projections must protect private company details while exposing
  useful trust signals.
- **SET-01**: Settlement must record the authorized economic outcome for a Task through
  policy-authorized Settlement Lines.
- **SET-02**: Baseline Node Validation must not be treated as a Compensable Contribution
  in task settlement.
- **PAY-01**: The default Solana payment path must use a modular Solana Payment Adapter
  that consumes the DAO Payment Interface.

## P2P, Compatibility, and UI

- **P2P-01**: P2P message envelopes must authenticate sender or relay identity without
  implying lifecycle authority.
- **P2P-02**: Every state-changing lifecycle event must satisfy Event Authority and
  Event Admission Rule before mutating state.
- **P2P-03**: Protocol and capability version compatibility must allow older nodes to
  participate when support is explicit and safe.
- **UI-01**: Operator UI must expose task intake, policy decisions, quotes, assignments,
  evidence, review, dispute, reputation, and settlement states.

## Quality, Security, and Performance

- **TEST-01**: Implementation must follow Jest-first BDD/TDD with unit, contract,
  integration, and end-to-end coverage sized by risk.
- **PERF-01**: Local preflight and policy decision must be measurable against the current
  p95 performance budgets.
- **SEC-01**: Secure node boundaries must protect secrets, wallets, workspaces, private
  evidence, local runtime configuration, and on-chain/off-chain data separation.
