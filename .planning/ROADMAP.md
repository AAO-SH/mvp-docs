# Roadmap

Status: v1 phased roadmap generated by GSD ingest.

Each requirement from `.planning/REQUIREMENTS.md` appears in exactly one phase for
traceability. Constitutional gates apply to every phase even when their IDs are owned by
Phase 1.

## Phase 1: Protocol Foundation and Safety Gates

Goal: create the project skeleton and core domain primitives that keep later work inside
AAO's constitutional boundaries.

Owns requirements: `P2P-01`, `P2P-02`, `TEST-01`, `PERF-01`, `SEC-01`.

Deliverables:

- strict TypeScript monorepo structure;
- Clean Architecture package boundaries;
- shared domain language and value object conventions;
- lifecycle event envelope, Event Authority, and Event Admission primitives;
- baseline Jest BDD/TDD harness;
- security boundary tests for secrets, wallets, workspace, adapters, and off-chain data;
- initial performance measurement harness for preflight and policy decisions.

Exit criteria:

- domain layer has no framework, transport, UI, storage, or Solana dependency;
- event admission tests prove signatures alone cannot mutate lifecycle state;
- quality gates can run locally through documented commands.

## Phase 2: Company, Policy, Agent, and Capability Registry

Goal: model governance, company policy, agent policy, pricing policy, and capability
resolution.

Owns requirements: `GOV-01`, `GOV-02`, `GOV-03`, `AGT-01`, `AGT-02`, `AGT-03`,
`AGT-04`, `CAP-01`, `CAP-02`.

Deliverables:

- Company models and governance authority rules;
- Company Policy and Task Policy evaluation;
- Agent Policy, Agent Permission, Agent Pricing Policy;
- local pricing configuration grant model;
- Global Capability Key and Company Capability Key resolution;
- Capability Support Manifest privacy boundary.

Exit criteria:

- policy decisions record exact policy and capability definition versions;
- company-scoped capabilities cannot leak through public support manifests;
- runtime pricing requests cannot bypass owner grants or pricing rules.

## Phase 3: Task Intake, Planning, Quote, and Budget

Goal: prevent invalid or unfunded agent work before runtime token spend.

Owns requirements: `TASK-01`, `TASK-02`, `MKT-01`, `MKT-02`, `MKT-03`.

Deliverables:

- Task Proposal, Project, Goal, and Task intake model;
- Preflight Check and Token Spend Gate;
- Execution Quote flow;
- Budget Reservation flow;
- bounded Planning Task decomposition and clarification path.

Exit criteria:

- invalid, unsupported, vague, unsafe, or unfunded tasks are rejected or routed to
  planning before agent execution;
- accepted quotes and budget reservations are traceable to policies and expirations.

## Phase 4: Assignment and Lease Protection

Goal: make task claiming safe against availability denial and interface confusion.

Owns requirements: `ASN-01`, `ASN-02`.

Deliverables:

- Executor model for Agent and human Stakeholder;
- Agent Adapter and Human Interface boundary;
- Assignment Lease lifecycle;
- release, reassignment, dispute, and escalation hooks.

Exit criteria:

- a task cannot have multiple direct executors;
- a human executor must be a Stakeholder of the same Company;
- expired leases cannot indefinitely block task availability.

## Phase 5: Evidence, Artifact Access, and Validation

Goal: make task completion evidence-first and privacy-preserving.

Owns requirements: `EVD-01`, `EVD-02`, `EVD-03`.

Deliverables:

- Evidence Bundle model;
- artifact references through Helia/IPFS-compatible ports;
- Artifact Access Grants;
- Validation Authority and Validation Result;
- deterministic validation rules and contract tests.

Exit criteria:

- no review, reputation, or settlement effect can occur without evidence validation;
- private artifact access is minimal, time-bounded, revocable, and auditable.

## Phase 6: Review, Dispute, and Anti-Abuse Controls

Goal: handle subjective judgment and dishonest or mistaken reviewers without giving any
single participant unchecked power.

Owns requirements: `REV-01`, `REV-02`, `DSP-01`, `DSP-02`, `DSP-03`.

Deliverables:

- Review Request, Review Decision, and Review Outcome;
- Dispute Case and Dispute Outcome;
- Dispute Resolver and Dispute Resolution Panel;
- Dispute Bond, Dispute Cost Allocation, and DAO-governed waiver rules;
- grant-gated dispute evidence access.

Exit criteria:

- challenged reviews can be resolved by conflict-free third parties;
- blocking disputes cannot be opened without bond, reserved cost, or DAO waiver;
- frivolous dispute cost handling is separate from Agent Slashing.

## Phase 7: Reputation, Settlement, and Solana Payment

Goal: derive trust and economic effects from validated, reviewed, and dispute-resolved
task outcomes.

Owns requirements: `REP-01`, `REP-02`, `SET-01`, `SET-02`, `PAY-01`.

Deliverables:

- Reputation Signal and privacy-safe Reputation Projection;
- Settlement and Settlement Line;
- Compensable Contribution rules;
- Payment Execution Record;
- modular Solana Payment Adapter consuming DAO Payment Interface;
- commitment-only on-chain data boundary.

Exit criteria:

- Settlement Lines are policy-authorized, attributable, and evidenced;
- baseline node validation cannot be paid through task settlement;
- Solana payment integration can be swapped behind the payment port.

## Phase 8: Compatibility, Operator UI, and End-to-End Hardening

Goal: make the protocol operable over P2P network flows with an understandable operator
surface.

Owns requirements: `P2P-03`, `UI-01`.

Deliverables:

- protocol compatibility and capability support behavior;
- P2P propagation and admission integration;
- operator UI state model;
- end-to-end flows across task intake, quote, assignment, evidence, review, dispute,
  settlement, and payment;
- accessibility and usability checks.

Exit criteria:

- nodes with supported global capability definitions can interoperate safely across
  compatible protocol versions;
- operator UI exposes the task lifecycle without leaking private data;
- end-to-end tests cover the happy path and at least one dispute path.
